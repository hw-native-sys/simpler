# 供给 seal：省去终值读取后的 FAA(0)

日期：2026-11-16。测量基线：main `42e0d7b97bea` + #3116 `e43d863e92c5`；候选只增加供给 seal 的读取优化。提交基线更新至 main `b2e3d0e98628e107054445e0171aae93f657d9e8`，其中 #3116 已合入为 `173706623`。该 main 与测量基线的 A5 HBG 源码及相关 C++ 测试一致；下面保留原批次数据，不将其标作更新 main 后重新测量。

## 修改前后与成立条件

`claim_seal` 表示本任务的有效 block 已全部有 owner，与计算及异步债务均归零的 DONE 分开。`scheduler_task_supply_closed` 在本核证明未命中、原完成字尚未 DONE 时检查它；0表示尚未观察到供给关闭，值等于本任务 block 数才表示已关闭。

原实现沿用“atomic 发布的字须经 atomic 确认”的保守读取契约，见提交 `1568c3da1` 的 `scheduler_memory.h`。`ld_dev` 只作低成本提示：读到0就继续等待，避免每次未就绪轮询都发起原子操作；读到非零后，再经返回型 FAA(0) 取得原子路径的快照，之后才判定关闭或非法值：

```cpp
uint64_t seal = scheduler_gm_query(control->claim_seal);  // A5: ld_dev
if (seal != 0)
    seal = scheduler_gm_fetch_add(control->claim_seal, UINT64_C(0));
```

这里 FAA(0) 的用途是确认读值，不是领取 block 或更新完成计数；加0虽然数值不变，仍是返回型原子操作。原来的额外确认来自上述统一契约，不能据此断言硬件曾经读错 seal。

当前沿用 #3116 对可靠终态快照的读取契约，并对供给 seal 明确以下边界后，直接使用第一次读值：

```cpp
const uint64_t seal = scheduler_gm_query(control->claim_seal);  // A5: ld_dev
```

- 读取必须满足当前采用的可靠64位 `ld_dev` 契约。绕过 scalar DCache 本身不等于自动获得任意 atomic 或跨地址内存顺序保证，也不是本次删除的全部依据。
- 任务身份在当前 run 内固定；seal 只由最后一个有效 owner 从0发布为本任务 block 数，协作任务仍先完成所需成员登记。该终值不撤销、不在当前 run 内复用。读到旧0只会延迟观察；可靠读到终值已经足以证明关闭，追加 FAA(0) 不再提供新的供给事实。
- 该读取只建立 SUPPLY_CLOSED，开放后项领取，不授权执行。真正的领取原子操作、seal 发布写入及屏障、执行前 DONE 检查和 payload 接收屏障都保留。AICore 上的跨地址顺序由显式屏障承担，不能把包装函数的 `order` 参数当作硬件 acquire 保证。

两种读法之后的判断相同：0继续等待，等于 block 数则缓存 SUPPLY_CLOSED，其他非零值仍报错。协作成员退休所用的独立 `scheduler_read_claim_cursor` 校验路径保持不变；此结论不能直接推广到会回滚或复用的计数、所有权 CAS，以及其他地址的 FAA(0)。

省去的开销发生在本核尚无缓存证明、读到正向 seal 的供给检查中，多个核可分别受益；它不要求观察者恰好是完成该任务的核。删除后减少同一 seal 地址上的返回型原子请求及等待，但实际 L0 收益取决于这些等待是否影响执行进度，不能把原子次数或跨核耗时之和直接换算成墙钟收益。

## 验证与收益

新测试覆盖 AIC/AIV 的零值、合法终值和非法 seal：不再执行目标 FAA，同时供给关闭仍不能放行尚未 DONE 的执行依赖。4个 CPU 套件、A5 的24个资源作业和5项 L2 检查通过，设备 IR 扫描16/16零发现。

移到 main `b2e3d0e98` 后，重新构建 A5 onboard/sim：AICore 二进制 SHA-256 与上述实测候选一致，Host 库随主线更新重新构建。4个 CPU 套件、A5 模拟的4个资源作业及5项 L2、单卡 A5 的2个资源作业及5项 L2 均通过，完整 pre-commit 检查通过。该轮只复核功能和构建，不新增性能样本。
