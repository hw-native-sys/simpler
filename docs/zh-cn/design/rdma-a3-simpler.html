3. 总体流程

  1. 应用通过既有通用编译/装配流程构建并注册普通 ChipCallable，与 SDMA 接入方式一致。Worker.init() 启动执行环境并准备 Host Orchestrator，不自动创建本次通信域。
  2. 应用调用 Worker.run(rdma_host_orchestration,...)；运行时执行该 Python Host 编排函数，由其显式调用已有 allocate_domain() 或 get_or_allocate_domain()，请求 workspace_engines=("rdma",)。首次创建域时延迟建立基础 communicator。
  3. simpler A3 平台层分配本地设备窗口，调用 PTO 的 GetCommWorkspaceSize()、BuildComm()，得到 MR、AI QP、RDMA workspace 和各 rank 的显存地址。
  4. 每次调用通过 TaskArgs 传递 context、peer、本地/远端偏移、长度和 QP 号。orch.submit_next_level() 提交同一个 callable，不重新注册 MR/QP。
  5. Chip orchestration 使用已有 rt_submit_aiv_task() 派发 AIV kernel_entry()；AIV 在提交前确认完成记录容量，再调用 BuildAsyncSession<RDMA>() 和 TPUT_ASYNC/TGET_ASYNC<RDMA>()，随后复用 register_completion_condition() 登记事件。
  6. NIC 执行传输。AIV 返回并发布普通 FIN；AICPU 只读查询 IN_DIE CQ 的成功前缀。FIN 与真实传输完成都满足后，运行时才完成 TaskId 并释放后继依赖。

4. 数据路径与首版范围

业务数据路径是 本 rank NPU HBM → A3 板载 RoCE → 对端 NPU HBM，GET 的方向相反。Host 负责资源、Bootstrap 和调度；Host 的文件/控制消息仅交换连接信息，不中转业务 payload。远端 VA 是 MR 寻址信息，不能当作本地可解引用的 peer mapping。

首版支持 A3、platform="a2a3"、TMR、同一 Host 的双 rank L3、设备内存窗口、连续字节 PUT/GET、持久窗口和多次调用。PTO 支持 A2 不等于 simpler 的 A2 已经验证；更多 rank、HBG、跨 Host L4、Host-backed RDMA、通知操作、任意 Tensor 自动注册及 InCore 融合不在本次范围。

CommWorkspaceKind.RDMA 已存在，无须新增枚举值；RdmaConfig 已存在，但要补齐 A3 的 QP/地址/端口配置。现有 allocate_domain() 的公开签名保持不变，其 A3 实现必须修改：当前非零 workspace_mask 被拒绝，原有 Fabric/IPC peer 映射路径也不能直接承担 RDMA-only 资源准备。

PUT 完成表示本次 RDMA 写的传输完成，不表示远端业务已消费；GET 要求远端源在读取期间保持稳定。跨 rank 的数据就绪、消费和下一轮覆盖许可仍由应用阶段协议保证。

5. 资源边界

每个 rank 有独立的 Host owner 和 GM CommContext。simpler 的 CommContext 与 PTO 的 pto::comm::domain::CommContext 是不同类型：前者是现有 simpler 设备 ABI，后者是 Host 侧 provider owner。禁止互相强转。

Host owner 持有业务窗口、PTO workspace、PTO 临时设备 context、PTO domain owner、端口租约和状态。最终仅向 AIV 发布 simpler context：rankId/rankNum/winSize、各 peer 的 MR VA，以及 workspaces[RDMA]={addr,size}。RDMA-only 域无需导入 peer Fabric/IPC mapping。

该 Host owner 是现有 DomainAllocation 的扩展字段，不新增 A3RdmaDomain 类及 Prepare/Close/Abort 生命周期。初始化保留文件内 domain_alloc_via_rdma() 和必要的 HostExchange 回调；校验、端口协调、释放与失败保留接入现有路径。SDMA/PTO 复用边界见接口清单。

业务窗口属于应用数据；workspace 属于传输元数据。PTO 自动路径可能按自身公共约定初始化 signal prefix，simpler 不把该 prefix 作为新增用户通知能力；新域初始化完成后才公开，复用命中不再调用 BuildComm、不重置数据。业务 CommBufferSpec 的 carve 仍由 simpler 管理，不把 UB scratch 或 provider operand 页算进用户窗口。

独立模板的入口逻辑如下，实现在 builtins/rdma/rdma_orchestration.cpp：

extern "C" __attribute__((visibility("default")))
OrchestrationConfig aicpu_orchestration_config(const ChipTaskArgs &) {
    return OrchestrationConfig{.expected_arg_count = 6};
}

extern "C" __attribute__((visibility("default")))
void aicpu_orchestration_entry(const ChipTaskArgs &args) {
    if (args.tensor_count() != 0 || args.scalar_count() != 6) {
        rt_report_fatal(SIMPLER_ERROR_INVALID_ARGS, "RDMA expects six uint64 scalars");
        return;
    }
    CoreTaskArgs core_args;
    for (uint32_t i = 0; i < 6; ++i) {
        core_args.add_scalar(args.scalar<uint64_t>(i));
    }
    rt_submit_aiv_task(0, core_args);
}

模板只做入参形状检查和任务转发；MR/QP 资源由 Host domain owner 准备，请求字段合法性与完成容量由 AIV checked helper 校验，完成事件由 AICPU completion backend 汇合。op/子内核绑定及产物 ABI 在构建装配合同中校验，不塞进 OrchestrationConfig 的计数字段。

A3 请求参数与真实完成协议

返回设计入口

1. 每次触发如何传参数

同一个已注册 callable 可多次提交，每次的六个 uint64 是独立 TaskArgs。固定 ABI 见接口清单。例如同一个域可以先 PUT local+0 → peer+4096, 4096 B，下一次 GET peer+8192 → local+16384, 2048 B；更换 offset/peer/长度不需要重新编译或重新注册 MR。

参数 PUT GET
comm_context 当前 rank 的 simpler GM context 相同
peer_rank 远端目标 rank 远端源 rank
local_offset 本地源窗口偏移 本地目标窗口偏移
remote_offset 远端目标窗口偏移 远端源窗口偏移
nbytes 搬移字节数 搬移字节数

构建出的普通 chip orchestration 将它们交给 AIV；不是把这些值写死到 Host 注册 callback，也不通过 CCU task args 传递。TaskArgs 和 CoreTaskArgs 的内部表示不一定就是 48 B 连续内存，六个逻辑 uint64 的次序和取值才是两个边界必须共同遵守的合同。

AIV 在发 WQE 前检查：有效 TMR AsyncCtx、非空 context、当前任务对应的有效域、RDMA workspace 范围、magic/version/IN_DIE、rank/peer/QP、peer 非自身、窗口与 MR 一致、地址加法不溢出。首版要求 nbytes>0、nbytes<=0x7fffffff，offset 和长度均为 64 B 倍数；这是 simpler 的保守合同，不声称是 PTO 的最小硬件对齐要求。

所有范围使用 offset <= extent && nbytes <= extent-offset 校验，不能先相加再比较。先在 64 位上判断 peer/QP 范围，再窄化。远端地址只用于 PTO tensor 的 MR 寻址，AIV 不以普通 load/store 访问它。

2. AIV 提交与完成登记

  1. kernel_entry() 解析参数并校验；获取本任务的 AsyncCtx。
  2. helper 检查 task token、count/entries/error 指针、已有错误和容量；要求当前 count 小于 capacity。容量不足时在发 WQE 前失败。首版每次 kernel 只发一个 PUT/GET event，所需容量上界为1。
  3. 使用独立 UB scratch 建立 BuildAsyncSession<DmaEngine::RDMA>()。公共 scratch 大小沿用 PTO 的 kRdmaScratchBytes=256，不侵占业务 GM；IN_DIE 的具体最小值不能替代通用接口约定。
  4. 独立 wrapper 独占 pipeline event 0 和 UB scratch；组合业务调用 checked helper 时由调用者分配合法 syncId，使用 qp_index，发起 TPUT_ASYNC<RDMA>(...,peer) 或 TGET_ASYNC<RDMA>(...,peer)。
  5. PTO Post() 在 MR 检查后进入 Reserve/Lock，生成 WQE，通过 MTE 写 NIC 可访问 SQ 并提交 SQ doorbell，返回事件。
  6. 校验 postFailed、非零 handle、error-handle 和 CompletionRecordCount/At()。成功事件必须解析到 RDMA_IN_DIE_CQE，记录地址与当前队列匹配。
  7. 构造 CompletionToken，调用已有 register_completion_condition(ctx,token) 写条目并更新 count，再执行 defer_flush(ctx)；AIV 之后返回普通 FIN。

内置 wrapper 使用动态长度、连续一维的 uint8_t GlobalTensor 表示 payload，形状长度就是 nbytes，不把字节数乘成元素数。PUT 的 dst 是 peer MR VA 加 remote_offset，src 是本地 MR VA 加 local_offset；GET 的 dst/src 相反。这样相同内核可处理不同业务 dtype 的窗口字节，不为每种 dtype 重编译一个搬移实现。

session 采用 peer-independent 重载 BuildAsyncSession<RDMA>(scratch,workspace,my_rank,session,sync_id,qp_index)，随后在 PUT/GET 调用中显式传 peer。sync_id 必须满足当前 IN_DIE 的 0～7 范围，并由 wrapper 的 UB/流水线资源分配保证与同一 AIV 内其他事件不冲突；不能把 TaskId 或 peer_rank 当 sync_id。

直接复用登记函数成立的关键是 slab 所有权：本任务的 AIV kernel 在返回前独占该 slab；从容量检查到登记之间，不调用其他会消耗其槽位的 simpler API；PTO 的 RDMA 提交只操作自己的 session/队列，不写这个 AsyncCtx。共享 QP 的不同任务仍有独立的 slab，因此 QP 多核并发不会抢占本任务的完成槽。

现有 A3 SDMA send_request_entry() 已在发起传输前检查所需容量，然后调用最终使用 register_completion_condition() 的登记路径。源码中明确说明 kernel 返回前没有其他 writer 消耗这些槽位。本设计沿用这一模式，无需新增登记或取消 API。

仍须检查 register_completion_condition() 的返回值。在上述不变量成立且内存有效时，提交后不会因容量耗尽而失败；若仍失败，应视为 runtime 不变量或上下文失效，记录错误并保留已提交请求的 owner，不调用 event.Wait 兜底，也不伪装为“未提交”。不得在发布 FIN 后补写记录。未来若改变为多 writer 或允许交错调用消耗同一 slab，必须先修订该所有权协议；已知 N 个事件的单 writer 批量提交也可先检查 N 条容量。

PTO 的 AsyncEvent.valid() 只判断 handle 非零，不代表成功；error-handle 也可能非零。TestEvent() 返回非 pending 也可能包含失败。simpler 必须检查状态，不能把这些布尔结果当作成功完成。

IN_DIE 的 Reserve() 本身可能等待锁或队列空间，并可能调用 AIV Progress()，当前源码有内部 cycle timeout。因此本设计的“异步”表示不在 AIV 等待本笔传输完成，不承诺提交路径严格 wait-free。无需把 PTO 的锁或回收逻辑再移植进 simpler。

3. 完成 token、CQE 与游标所有权

事件编码和资源身份

PTO 事件高 32 位为 queueIndex=peer*qpNum+qpIdx，低 32 位为提交后的目标 SQ head。高字 0xffffffff 表示错误。IN_DIE 在 32 位 head 耗尽前返回错误，不能自行允许整数回绕或仅用有符号差值推断无限复用。

simpler 条件保存完整 handle、workspace 地址和当前 TaskId 身份。domain generation 由既有 run lease 关联，只有旧 run 的设备访问已静默才允许释放和重用地址。每次登记清空条件的私有 cursor，TaskId 派生身份仅用于该条件内部校验，不被宣称为跨 run 的唯一 generation，也不增加 token ABI 字段。

PTO record 提供目标 CQE 地址、预期 owner 和 kind。AICPU 可用它交叉验证，但首版以“完整事件目标 + 已成功回收前缀 + 有界 CQE 扫描”查询：一个 CQE 地址和一个 owner bit 不足以防止 AIV 回收后绕圈覆盖，也无法表达此前 SQ 项的错误。

只读 observer

IN_DIE 的 Queue 包含 sq/cq Ring、错误字段和 AIV tournament gates。Ring 提供 GM buffer、doorbell、head/tail 地址、深度和 stride。所有布局从固定 PTO 的 Host-safe rdma_workspace_types.hpp、in_die_types.hpp 获取；不得复制旧版 HNS1825 结构。

唯一修改 CQ 消费位置的主体是 PTO AIV Progress()。 AICPU 不写 cq.tail、sq.tail、Queue.error，不敲 CQ doorbell，也不参与 AIV 的 COREID tournament lock。实现采用每条件私有 cursor，访问受既有 AsyncWaitList 锁保护；多个条件没有共享缓存，也不把 cursor 写入 PTO Queue。

poll_rdma_in_die_event() 的算法：

  1. 验证 owner/generation 和全部地址范围；读取并校验队列实际深度、stride=32、target 非零且不超过已发布 SQ head。
  2. invalidate 相应 cache line，acquire 读取 PTO cq.tail。这是 PTO 已逐项检查成功的前缀。如果 tail>=target，可报告该事件完成；后面新出现的错误不追溯否定这个已成功前缀。
  3. 从 max(tail, observer.success_prefix) 扫描到 target，每次 tick 最多扫描 32 项。每项地址是 cq.buffer+(index & (depth-1))*stride。
  4. 使用 同一个 word0 快照判断 owner 和 status。owner 是 (word0>>7)&1，ready 预期为 (index & depth)==0 ? 1 : 0；ready 后 status=(word0>>8)&0xff 必须为 0。
  5. 读取每个 CQE 后重新 acquire 读取 tail。若 tail 已越过该项，采用 PTO 已确认的成功前缀，丢弃可能属于新一圈的快照；若 tail 未越过该项，基于“SQ/CQ 最多 outstanding depth-1，未回收槽不可重用”的 PTO 不变量解释快照。
  6. owner 未就绪返回 PENDING；发现错误 CQE 返回 FAILED 并缓存该绝对错误位置。不能只检查最后一项，也不能因后续成功 CQE 覆盖而丢失错误。
  7. 只有逐项扫描或已回收 tail 证明整个目标前缀成功，才返回 READY；扫描到更早已缓存的失败位置时返回 FAILED。最后执行适合 AICPU 的 acquire/设备可见性屏障，沿既有调度协议释放后继。

这个 observer 不推进硬件 CQ。队列逐渐满时，PTO 下一次 Reserve() 调用自己的 Progress() 回收；少量请求完成后即使 tail 尚未更新，AICPU 也可凭真实 CQE 完成任务。关闭时确认所有已提交 target 完成，再由 provider 销毁 QP，不为清空计数而伪造 tail。

必须验证的硬件前提

上述只读算法是 simpler 的设计，并非 PR 2155 已提供的 AICPU 查询 API。它依赖 HCCP 返回的 CQ buffer/tail 所在 GM 可被 AICPU 正确访问，以及 IN_DIE 的有序 CQ 语义。集成时需要在实际 A3 SDK/驱动验证；编译可见的结构体不能证明这些硬件性质。

仓库当前 cache-coherency.md 已列出可选 A3 IN_DIE 后端的 CQE 保守失效策略，不能套用 A5 的“无需 invalidate”。本设计采用 A3 DMA 读取的 cache maintenance，并要求 observer 对 PTO 数据页始终只读，避免 clean+invalidate 将 AICPU 脏数据写回覆盖 provider 状态。具体内存属性、刷新范围、完成屏障，以及 CQE 发布与绕圈复用仍须通过 A3 硬件验收。

若发现任何前提不成立，应先在 PTO/provider 增加正式 Host-safe 完成快照能力并同步设计，不能退回“FIN 就完成”、Host 代理 payload 或竞争写 CQ tail。AICore 无法访问 SPR 控制窗的限制也不能靠自定义 MMIO 规避；NIC doorbell 仅使用此 PR 的正式路径。

4. FIN 汇合、错误与数据可见性

TMR 完成需要 normal_done && all_registered_conditions_ready && no_error。AIV 发出 WQE、AIV FIN、Host submit 返回、CQ owner 尚未更新都不是成功条件。AIV FIN 早于 CQE时等待网络；CQE早于 FIN 时仍等待正常执行结束。

既有 SchedulerContext::drain_cancelled_run() 增加 ROCE/type4 分支：先按原协议确认 AIV 已停止，再用同一只读 observer 检查 wait-list、mailbox 和 slab 中的事件。只有真实 CQ 成功才确认该条件 drained；错误或超时保留 owner，不完成 TaskId，不释放失败图的依赖。raw slab 条件按当前 TaskId 初始化私有观察身份。

GET 后续本地消费者必须通过完整完成的依赖再读取目标，沿用 TMR 的 AICPU→AIV 派发和 cache/流水线协议；AICPU 的普通 acquire 不能单独替代 AIV 的 GM 可见性处理。PUT 的本地源到传输结束前不可覆盖；远端目标消费仍需要应用阶段协调。

错误发生点 处理
参数、能力或 completion 容量错误，确定未提交 失败结束本任务，不发 WQE，不阻塞等待

retire 只清空当前条件的私有 cursor，不改变 PTO 的队列，也不会清除其他条件的观察状态。每次新登记重新初始化 cursor，避免跨任务/跨 run 缓存污染；工作区本身由 domain generation/run lease 保持存续。资源清理由生命周期协议统一控制。

5. 多次触发与并发边界

多任务可以发往同一个 peer/QP，PTO 的 AIV lock 保证 WQE 发布；但不同任务访问重叠窗口范围仍须用 TaskId/deps 串行化。QP 排序不等于应用数据竞争已解决。多 QP 和多 rank 不提供隐式全局顺序。

内置 callable 每个请求只派发一个 AIV block。重复或并发请求在不同物理 AIV 上运行时使用 PTO 的 COREID 锁；不在同一 AIV 上创建可重入发布流。实际 QP 数以域配置和 provider 结果为准，不能一直按 peer*qpNum 固定选择 QP0。

任务只能访问同一有效域的窗口。首版没有跨 domain 请求，也不把普通 Tensor 地址直接变成临时 MR。若业务输入在普通 Tensor，应用通过既有 copy 机制放入通信窗口并建立依赖后，再调用该后端。

域内 rankId 按 members 顺序密集编号。physical device id、Worker chip id 和 domain rank 是三种身份，Bootstrap 必须明确转换，不能取 rank % device_count 替代 Worker 真实设备选择。

2. 初始化及全 rank 发布

现有 DomainAllocation 的 RDMA 初始化分支

  1. L3 parent 校验 members、DEVICE backing、TMR、RDMA-only、窗口 carve 和一致配置。在派发任何业务任务前完成同步域准备。
  2. coordinator 按有序 members 分发相同 QP 数、端口请求和各自 local IP。自动请求以 0 编码；native 使用相同 run_token/allocation_id 提议候选并全 rank 投票。记录 owner 身份和绝对截止时间，保存端口独占锁，并在任何 BuildComm 开始前完成预留确认。
  3. native 复用已有 DomainAllocation，追加 PTO Host context、外部 GM 分配、端口占用记录和状态字段，尽早放入已有 pending owner map。初始化使用文件内 domain_alloc_via_rdma()；不增加另一套 owner 类和 Prepare/Close API。析构不得替代有返回状态的清理，异常不能让已注册资源失去 owner。
  4. aclrtMalloc 创建本地窗口，记录实际 owner/extent。注册和 CommContext.winSize 对外统一采用已协商业务 extent，不能各 rank 按不同物理 padding 生成不一致 MR。
  5. 配置 PTO CommConfig：RDMA-only、rdmaOptional=false、显式 deviceId/dense rank/rankNum、symBytes、qpNum、basePort、localIp；设置 HostExchange。使用 RDMA-only 的 callback Bootstrap，无需为每个域再创建 HCCL communicator。
  6. GetCommWorkspaceSize() 查询并分配三块独立外部存储：业务窗口 rdmaSymmetric、RDMA workspace、PTO 临时设备 context。业务窗口已经存在时将其绑定，不能重复申请一份未被应用使用的窗口。
  7. BuildComm() 负责能力/地址协商、HCCP 服务/rdev lease、业务 MR 和 operand MR、socket 连接、AI QP、MR/QP 绑定、QP ready、GM metadata 及 peer 地址回填。
  8. 复用 PTO 的配置/建链检查，在分配分支校验 rdmaReport=Ready、IN_DIE/v3 和 simpler 窗口/工作区 extent 等接入条件；不增加独立 validate API。读取 PTO 的 Host context，逐字段转换为 simpler CommContext，复用 comm_domain_onboard::upload_context() 上传镜像。
  9. PTO 完成全 rank ready agreement 后，复用 Worker 既有分配请求 join/abort：所有 native context 准备成功后才发布 Python handle。任何 rank 失败都不发布半成品域，不增加另一套公开 prepare/commit 协议。

PTO BuildComm() 既有的可选后端降级不在本设计使用：RDMA-only 要么完整 ready，要么失败。已有 base HCCL 环境和 PTO HCCP 服务共享必须尊重其 owned/borrowed 标记；域关闭不得关闭由 HCCL 持有的服务。

HostExchange 的协议

使用已有本机 allocation 控制会合机制实现 callback，首版不新增 MPI 依赖。会合键至少包含 run_token/allocation_id/generation/stage/round；文件采用写临时文件后原子发布，不允许把上次失败遗留文件当新回复。

保留一个私有 domain_host_all_gather() 适配函数，复用 marker 路径、原子发布和有界等待，增加记录汇集。PTO 的 HCCL all-gather 只有在 communicator 与 domain 的成员和顺序完全匹配时可用；本设计支持任意 members 子集，不借用可能更大的 base communicator，也不新建每域 HCCL communicator。普通 file barrier 不能传递初始化记录。

callback 接收 PTO 的固定长 Host 记录；外层保存版本、长度、rank 数、stage 和校验信息，按 dense rank 顺序返回。所有参与者必须调用相同序列，失败也要结束已派发的请求后再进入 abort。外层协议逐字段编码，不把 C++ padding 或 Host 指针当稳定网络格式。

PTO callback 的 payload 按不透明字节承载，字段解释由固定版本的 PTO 负责；该路径只用于同一 Host、同一构建 ABI 的参与者，不承诺将这些原始记录作为跨架构的稳定 wire ABI。外层 header 使用文本字段，payload 使用定长十六进制编码，避免二进制 NUL 截断。

PR 2155 的 Connection::Exchange() 另外负责通过 HCCP socket 交换业务 MR 的 base/size/rkey、rank 和 QP 数，并检查预先协商的 peer base。simpler 不重复发送 lkey，也不发明另一套 QP 私有数据格式。

端口租约

同一物理设备的多个 RDMA 域不能无条件同时监听 60032。parent 派发的 native 分配事务在建链前为所有参与设备取得同一个空闲 base port，租约归 run/allocation owner 所有。

自动模式先提议端口，再全 rank 预留/确认；任一失败则撤销本轮预留，并在尚未开始 QP 建链时选择新端口。显式端口冲突直接报错。当前实现使用每 UID/物理设备/端口的文件独占 flock，持有 fd 即代表进程内 owner；进程结束时内核释放锁。打开时检查 inode、文件所有者和链接数；不 unlink 活跃的锁文件。该约束覆盖同 UID 多 Worker/进程；不同用户及外部 HCCP 应用仍由 provider 检测实际冲突，不能只凭“Host TCP bind 成功”断言 HCCP 端口可用。

外部 HCCP 应用未参与租约时仍可能冲突，provider 失败必须按初始化失败清理，不自动在部分建链后盲目重试。租约在所有相关 QP/socket 成功销毁后释放；失败 owner 保留租约防止误复用。

PTO 的 TryDestroyComm() 保留可继续清理的 provider 状态；外部 GM 的 aclrtFree() 出错则不同：调用可能已产生释放副作用，simpler 将 owner 标记为 terminal cleanup failure，后续 close 只报告 retained，不自动再次 free 同一地址。诊断 owner 仍在原 map 中，析构不替代有返回状态的清理。

端口协调逻辑接入现有 _allocate_domain() 和 native RDMA 分支，占用 fd/实际端口保存在已有 owner，释放在既有清理路径完成。不新增 RdmaPortLease 类接口；当前 SDMA/PTO 没有提供可直接套用的多域端口分配器，仍需补这部分私有实现。现有 GenerationLease 使用共享锁保护 generation 文件回收，不能用来排斥同设备同端口的另一个 owner。

5. 结束、失败与保留

正常释放顺序：停止接收新请求 → 本地所有 AIV FIN 和 RDMA 条件完成 → 业务确认所有远端访问静默 → 全 rank release agreement → TryDestroyComm() → 释放 PTO/业务/context 外部 GM → 释放端口和 owner。已有 C ABI 的 collective release 可以承载会合，但不能用一次 barrier 证明调用方没有尚未提交的业务访问。

实现入口复用 comm_release_domain_windows() / comm_abort_domain_windows() → release_domain_allocation()；RDMA provider 与内存的清理加入既有 release_domain_windows() 分支。正常 release 的静默协议和 initialization abort 的 parent join 前置条件保留区别，底层清理机制共用，不新增 Close/AbortInitialization 方法。

当前 A3 清理路径存在“barrier 超时也释放本地状态”和 map erase 路径。新增 RDMA 分支必须改为 fail closed：不能在远端还可能访问已注册窗口时继续 free，也不能因清理函数返回错误就丢掉 owner。

状态 可否提交 允许的动作
PREPARING 否 继续阶段协商，或所有准备请求终止后调用既有 comm_abort_domain_windows
READY 是 受依赖和范围约束提交，或开始静默关闭
QUIESCING 否 等待已知任务和应用远端阶段，不重置队列
INIT_RETAINED 否 返回 INITIALIZATION_ABORT_REQUIRED；join 全部准备请求后按 owner 记录清理
RUN_RETAINED / CLEANUP_UNCONFIRMED 否 返回原错误并保留环境、窗口、QP 和端口；需明确恢复证明，普通 close 不盲目重试

PTO Finalize() 可在 Init 失败后仍持有资源；调用方只能依据其明确成功结果释放 caller-owned GM。正常运行未知完成与纯初始化残留不能混用同一种 abort。普通接口不宣称具备设备错误后的自动恢复能力；无法证明静默时保留 owner 并报告未确认回收，不执行设备 reset 或隐式重发 PUT/GET。

2. 工具链与构建接入

基线要求是可编译 __NPU_ARCH__=2201 的 CANN/Bisheng、匹配 A3 的 driver/firmware、匹配运行时的 HCCP 头文件和 libra.so/libtsdclient.so。PR 2155 明确要求 hccp.h/hccp_common.h，还使用 infiniband/verbs.h、driver 和 tsd 声明；不能自行镜像私有结构来消除编译错误。

4. A3 双 rank 实机验收

  1. 在真实 A3 的同 Host 两个设备建立域。核对 SoC、logical→physical id、RoCE IP、业务 MR base/size、QP ready，确保未误选普通 Host NIC。

  3. 一个 callable、一个 domain 连续多轮复用；交替 peer/offset/长度并验证数据确实随参数改变。复用期间 MR/QP/端口不重新创建，业务内容按显式 reset 策略保留。
  4. 多 AIV task 发往同 peer/QP、多 QP 分流，累计超过实际 CQ 深度数倍，以确认 PTO 回收和只读 observer 不因 owner 绕圈误判。记录实际 HCCP 深度，不能用源码请求8192当作设备一定返回的值。
  5. 用可观察阶段 gate 确认 FIN-before-CQE、CQE-before-FIN、CQE cache 刷新和 GET 后继读取；只有传输与正常执行都完成，后继才能消费。
  6. 在 SQ 未满前提交少量请求，确认 observer 在 PTO tail 尚未推进时可读真实 CQE；再提交足够请求确认 AIV Reserve/Progress 回收仍工作。
  7. 确认 AICPU 能访问真实 CQ buffer 和 software tail；验证 CQ owner/status 与固定 PR 源码一致。若不成立，停止集成并修正 provider 完成接口，不编造成功路径。
  8. 正常关闭再创建、显式端口冲突、链路/peer 失败和超时分别验收。故障注入发生在可观察提交阶段，校验 live owner 不被提前 free；这类用例需要受控设备，不在无设备环境假装执行。
