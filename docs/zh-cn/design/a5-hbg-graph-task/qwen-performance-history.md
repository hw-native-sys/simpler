## `inv_rms` 输入缓存修复

各层复用同一个 64-byte `inv_rms` scratch。生成的 RoPE 内核使用 scalar load 读取它，
resident 不执行 legacy 的每任务全 DCache 刷新，因而可能读取前层的缓存副本。
修复位于共享 attention wrapper：在 RoPE 消费前对该输入执行一次 `dcci(SINGLE_CACHE_LINE)` 和 `dsb(DSB_DDR)`。
不修改生成的计算公式、依赖边、输入、golden 或容差；37 个 incore 的实际 hash 仅 func_id=12 改变。

任务 `task_20261102_121325_5596846344` 在设备 3 配对执行主线/候选三轮，完整 out/K/V 均通过。
V 当前 token 的 655360 元素全部在容差内，最大绝对差 0.03125；修复前两个候选独立进程均有十万级超差。
数值证据和修改前后 kernel hash 见 修复验证数据（本地 `qwen-cache-fix-validation.json`）。
候选三轮 Device 为 65.717 / 64.883 / 64.895 ms；此修复解决正确性，性能退化另行定位。

同设备 3 的原始 native 对照再次复现：当前 token V 有 123486 个元素超差，最大绝对差 6.5625；
仅改变 func_id=12 输入缓存观察的版本已通过，排除了仅因换卡而通过的解释。
另一次 L4 采集的完整 golden 通过，独立 v6 协议审计验证 237088 个事件、11165 个设备逻辑节点、
19208 次 kernel execution、641 个 cooperative task；没有把普通 `deps.json` 的外层 DAG 当作内部依赖验证。
普通 dep_gen 只包含 45 个外层任务，直接使用会遗漏 Graph children；下节通过原始 Graph 来源补齐内部 DAG。

## 调度开销归因

设备 3 分别采集一轮主线和候选的 L3 trace，未同时开启 dep_gen，完整 golden 均通过。
使用另一次已审计的 v6 原始 Graph 来源展开 DAG，穿透 ENTER/EXIT/DUMMY，
得到 10604 个 kernel 节点和 23357 条依赖；两份 L3 的每个 task/block 执行数量均与展开结果一致。
记录、报告、kernel 统计及文件哈希见 DFX 摘要（本地 `qwen-dfx-summary.json`）。

`sched_overhead_analysis` 的依赖路径归因：主线 kernel/调度分别为 12.472/18.372 ms，
候选为 12.289/54.022 ms，调度部分增加约 35.65 ms。
`critical_path` 进一步计入实际 core 资源串行化，其路径组成不同：主线 636 个 task、compute/stall 为 19.191/11.648 ms，
候选 1092 个 task、compute/stall 为 27.542/38.750 ms。两套模型不能混作同一个比例。
该模型的 static CPM 下界为主线 15.307 ms、候选 13.954 ms；不是理论执行下界的增加造成实际耗时翻倍。

逐 kernel 的 L3 execution 中位数也未显示整体计算退化：Q projection 15.033→14.315 µs，
attention AIC 149.900→144.179 µs、AIV 147.081→146.160 µs，down projection（func 34）21.990→19.178 µs。
这些数据定位到派发等待和任务安排；具体优化需继续以无插桩对照验证，不能直接将 phase 的多核累计时间当作墙钟时间。
