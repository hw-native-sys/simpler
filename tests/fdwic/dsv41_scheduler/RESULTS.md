# DSV4.1 L0 性能基线

本文件维护 9 个 workload 的 PyPTO-lib 和 DSL 两版，共 18 组 L0 性能基线。
每次完整测量后直接更新本文件，历史基线由 Git 历史保留。
工作负载定义和准备方法见 [README.md](README.md)。

## 当前测量信息

- 更新日期：**2026-11-12**，时区 Asia/Shanghai。
- 验证结果：**18/18 组数值校验通过**；每组 1 次预热、10 次正式测量，共 180 个 case 测量样本。
- Runtime 源码：上游 main
  [cd16f9f6f](https://github.com/hw-native-sys/simpler/commit/cd16f9f6fc266bbddabd8a1b69bd39c469ad2ed9)，
  包含 #3005 的 own-slot 退休优化和 #3008 的 Scalar profiling 优化。
- 实际测量工作区及 runner 版本：
  [a013b1710](https://github.com/nalinaly/simpler/commit/a013b1710aee9d9fe7117ba249a709c3a64a3e43)。
  其中生产代码 `src/` 与上述上游版本一致；benchmark runner 保留了下文所述的 fork 启动对齐处理。
- 环境：Ascend950DT_9581（A5）、Linux aarch64、CANN 9.3.0；
  runtime 使用默认 `-O3 -g` 编译，实际 profiling level 为 L0，resident scheduler mode 为 1。
- 输入：现有 DSV4.1 测试输入，每个 rank 有 72 个有效 token、补齐至 80 行、64 个本地 expert，沿用原始零权重输入。
  数值校验针对这套固定输入的参考结果，不代表真实 checkpoint 的模型精度验证。
- Runtime、native runner 和 replay adapter 均从测量版本重新构建。
  复用固定输入和模型 kernel 二进制，并用新构建的工具检查 capture 记录布局、task/execution 数量及 kernel 镜像偏移。
- 所有上卡执行均通过 `task-submit` 持有设备锁。单卡组使用设备 2、3 或 7，具体见表；4 组 EP2 使用设备 2 和 7。

本次使用的
[runner](https://github.com/nalinaly/simpler/blob/a013b1710aee9d9fe7117ba249a709c3a64a3e43/tests/fdwic/dsv41_scheduler/production/runner.cpp)
先调用 `prepare_native_run`，待两 rank 的 Host 准备完成后对齐，再调用
`launch_native_run`、`wait_native_run` 和 `finalize_native_run`。预热与测量采用相同 profiling level。
上述上游版本的 runner 在 `worker.run` 前对齐，可能把对端 Host 准备耗时计入较早启动 rank 的设备等待。
**刷新时必须记录 runner 版本，并保持同样的启动计时边界，才能直接比较结果。**

原始产物集名称为 `l0-baseline-18-20261112`，其中保留了 `baseline.csv`、`samples.csv`、
`baseline.json`、`build-result.json` 和各 rank 的日志。
重算下表所需的原始样本也附在本文中，无需依赖私有目录。

不包含 Host 准备、编译、输入或前缀准备、预热耗时。
单卡组恢复已准备好的输入；EP2 在测量区间外重新生成前缀，case 本身包含真实通信耗时。

EP2 每次测量先取 `max(rank0[i], rank1[i])`，再对得到的 10 个值计算统计量。

## Runtime 编译耗时

A5 HBG runtime 使用新的构建目录进行干净编译，采用默认 `-O3 -g`，并设置 `CCACHE_DISABLE=1`。
Host、AICPU、AICore 三部分并行构建，每部分使用 8 个编译任务。
耗时包括 CMake 配置和编译；总耗时为实际经过的墙钟时间，不是三个组件耗时相加。

| 组件 | 耗时（秒） |
| ---- | ---------- |
| Host | 47.929 |
| AICPU | 5.591 |
| AICore | 356.059 |
| **总耗时** | **356.062** |

本次比 300 秒编译目标多 56.1 秒，AICore 编译决定了总耗时。
这是共享机器上的单次测量，不能据此直接归因与历史编译时间的差异。
计时范围仅覆盖上述三个 runtime 组件。Benchmark 工具在另一个进程中构建，部分时间与此区间重叠。
源码准备、模型 kernel 编译、设备排队和 benchmark 执行均不属于此计时范围。
未变化的 dispatcher 二进制直接复用，因此该数据不代表整个项目的安装耗时。

## 后续刷新方法

1. 原地更新本文件，保留文件名和 README 入口。记录测量日期、准确的 runtime 与 runner 版本、
   额外源码改动、硬件、工具链和编译选项。使用 Git 提交引用和直接文件比较即可，不要求计算内容 hash。
2. 构建匹配的 runtime、runner 和 replay adapter，按
   [准备说明](README.md#prepare-and-run) 获取兼容的测试包；
   检查 capture 布局，保持模型 kernel、镜像偏移和固定输入一致。输入或准备流程变化须明确记录。
3. 执行硬件架构检查，通过 `task-submit` 锁定设备。9 个 workload 的两版实现均运行 L0，
   每组 1 次预热、10 次正式测量，并保持上述启动对齐方式。
   检查实际 profiling level 为 0、resident scheduler mode 为 1，且每次运行数值校验通过。
   EP2 须保留两 rank 各自的样本。
4. 从成功的正式测量重新计算统计表并更新原始样本，排除预热及前缀耗时，EP2 逐次取最大值，保留慢样本。
   失败或缺失的 case 应在刷新 PR 中说明，不能混用旧数据和新数据并称为完整的新基线。
5. 按相同的干净构建、缓存和并行度口径刷新编译耗时；未测量时须明确标注。
   同步更新当前版本、结果表、原始样本、验证状态和编译数据，并在 PR 中提供原始产物及日志入口。
   沿用的历史数据保留原测量日期，不能归到新版本名下。计时协议发生变化时，应先说明再比较性能。
